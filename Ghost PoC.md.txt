# GHOST POC â€” Build Specification
## Grid Homeostasis & Orchestrated Self-healing Topology

---

## The Problem

Containerised services fail at runtime while humans are not watching.

A container crashes. Logs pile up. Nobody acts until someone is paged, wakes up,
logs in, reads the logs, understands the context, and manually executes a fix.
In that window â€” whether 10 minutes or 2 hours â€” the service is degraded or down.

The tools to detect and fix these failures already exist. The missing piece is the
**autonomous loop** that connects detection to action without a human in the middle.

### The Precise Question This POC Answers

> Can a lightweight agent system detect a known container runtime failure from a log
> stream and execute the correct corrective action â€” faster and more reliably than a
> human â€” with zero human input after start?

One question. One measurable outcome.
**MTTR (Mean Time To Resolve) with humans vs MTTR without humans.**

---

## What We Are NOT Building

- Not a full SRE platform
- Not a production system
- Not a cloud-connected agent
- Not an LLM-first system
- Not a framework evaluation
- Not specific to any workload type â€” web API, worker, database sidecar, batch job,
  or anything else running in a container

We are building the **minimum loop** that proves autonomous detection and resolution
works on synthetic log data. Nothing more.

---

## The Failure Domain

We are operating entirely in **container runtime failures** â€” things that go wrong
on infrastructure that is already running and already deployed. These four failure
modes account for the majority of unplanned downtime on containerised workloads
regardless of what is running inside the container:

| Failure | What Happens | Root Cause Class |
|---|---|---|
| OOMKilled | Kernel kills the process for exceeding memory limit | Resource ceiling too low |
| CrashLoopBackOff | Container fails to start repeatedly | Config error at startup |
| StartupProbeFailed | Health check fails, platform marks service unhealthy | Misconfiguration |
| HighLatency | Service running but response time exceeds threshold | Insufficient capacity |

These are **container runtime primitives**. Workload-agnostic. The Watcher does not
care what is inside the container. The Healer does not care what the service does.

### What We Are NOT Mitigating

- IaC failures â€” Terraform drift, wrong IAM role at provision time
- Cluster failures â€” node not ready, control plane unreachable
- Network failures â€” DNS, firewall, load balancer
- Storage failures â€” mount issues, corrupted data
- Security incidents â€” anomalous access, credential compromise

---

## The Two Agents

### Watcher
**Job:** Read a continuous log stream. Detect known failure signatures. Emit a
structured event when a failure is found.

**What it is:** A loop with pattern matching. Approximately 80 lines of Python.
No framework. No LLM. Pure deterministic logic.

### Healer
**Job:** Receive a structured event from Watcher. Look up the correct action.
Execute that action against the infrastructure state. Record the outcome.

**What it is:** An event handler with a decision lookup table. Approximately 60
lines of Python. No framework. No LLM.

### How They Connect
A single `asyncio.Queue` â€” Python built-in, zero setup. Watcher puts events in.
Healer reads events out. This is the loop.

## Infrastructure State (Fake Container Platform)

No real cloud account. No real cluster. No API keys.

```python
infra_state = {
    "app-service": {
        "status": "running",        # running | crashed | degraded
        "memory": "512Mi",
        "min_instances": 1,
        "max_instances": 1,
        "port": 9090,               # deliberately wrong in some scenarios
        "restart_count": 0,
        "latency_ms": 200
    }
}
```

Actions mutate this dictionary. The loop is fully self-contained.

## Agent Skills

Each agent has a **skills file** â€” a plain Python file that declares exactly what
that agent can and cannot do. Skills files are the **single source of truth** for
agent capability. Agents import from their skills file â€” they never define patterns
or decision tables inline.

---

### `skills/watcher_skills.py`

```python
# skills/watcher_skills.py

AGENT_NAME = "watcher"
AGENT_VERSION = "1.0.0"

# What the Watcher looks for.
# Each entry: failure_type -> list of strings.
# Match fires if ANY string in the list appears in the log message (OR logic).
# Generic container runtime signatures â€” workload-agnostic.
DETECTABLE_PATTERNS = {
    "OOMKilled":          ["OOMKilled", "exceeded memory limit", "killed process"],
    "CrashLoopBackOff":   ["Back-off restarting", "CrashLoopBackOff", "restart limit"],
    "StartupProbeFailed": ["Startup probe failed", "readiness probe failed",
                           "connection refused", "health check failed"],
    "HighLatency":        ["latency", "response time", "exceeds threshold", "timeout"],
}

# Severity levels the Watcher pays attention to. Others are ignored.
WATCHED_SEVERITIES = ["ERROR", "WARNING"]

# How often Watcher polls the log stream in seconds.
POLL_INTERVAL_SECONDS = 1

# Structure of every event Watcher puts on the queue.
EVENT_SCHEMA = {
    "failure_type": str,
    "severity":     str,
    "service":      str,
    "message":      str,
    "timestamp":    float,
    "raw_log":      dict,
}

# Hard boundaries. Watcher must never do these things.
CANNOT_DO = [
    "execute_actions",
    "modify_infra_state",
    "make_decisions",
    "call_external_apis",
]
```

---

### `skills/healer_skills.py`

```python
# skills/healer_skills.py

AGENT_NAME = "healer"
AGENT_VERSION = "1.0.0"

# Decision table â€” single source of truth for all action mappings.
# Each entry: failure_type -> (action_name, action_params)
# Healer does not decide what to do. It looks up what to do.
DECISION_TABLE = {
    "OOMKilled": (
        "scale_memory",
        {"memory": "1Gi"}
    ),
    "CrashLoopBackOff": (
        "reset_and_redeploy",
        {"restart_count": 0, "status": "running"}
    ),
    "StartupProbeFailed": (
        "fix_port",
        {"port": 8080}
    ),
    "HighLatency": (
        "scale_instances",
        {"max_instances": 3}
    ),
}

# Maximum time Healer is allowed to spend making a decision in seconds.
DECISION_TIMEOUT_SECONDS = 5

# Maximum time a single action execution is allowed to take in seconds.
ACTION_TIMEOUT_SECONDS = 5

# What to do if no decision table entry matches the failure type.
DEFAULT_ACTION = ("log_unknown", {})

# Structure of what Healer records after every action.
OUTCOME_SCHEMA = {
    "failure_type": str,
    "action_taken": str,
    "action_params": dict,
    "success":       bool,
    "duration_ms":   float,
    "timestamp":     float,
}

# Hard boundaries. Healer must never do these things.
CANNOT_DO = [
    "read_log_stream",
    "pattern_match",
    "modify_event_bus_directly",
    "call_external_apis",
]
```

## The Synthetic Data

All synthetic data is generated programmatically by `data/seed.py`.
No hardcoded JSON files. No manual data entry. Run seed.py once and all
three datasets are written to disk. Re-run with a different seed for
different random orderings.

### `data/seed.py` â€” What It Must Generate

`seed.py` accepts one optional argument: `--seed INT` (default: 42).
It writes three files to the `data/` folder and prints a summary when done.

---

#### Dataset 1 â€” Clean Failures
**File:** `data/clean_failures.json`
**Size:** 4 records â€” one per failure type
**Purpose:** Prove baseline detection. Pure signal, zero noise.
Used in Experiment 1.

Each record is a single log event that unambiguously matches one pattern
from `watcher_skills.DETECTABLE_PATTERNS`.

```python
CLEAN_FAILURES = [
    {
        "severity": "ERROR",
        "service": "app-service",
        "message": "OOMKilled: container exceeded memory limit 512Mi",
        "labels": {"reason": "OOMKilled"}
    },
    {
        "severity": "ERROR",
        "service": "app-service",

        "labels": {"reason": "CrashLoopBackOff"}
    },
    {
        "severity": "ERROR",
        "service": "app-service",
        "message": "Startup probe failed: connection refused on port 9090",
        "labels": {"reason": "StartupProbeFailed"}

        "service": "app-service",
        "message": "Response time 7200ms exceeds threshold 5000ms",
        "labels": {"reason": "HighLatency", "latency_ms": 7200}

```

`seed.py` adds `timestamp` and `id` fields to each record before writing.

#### Dataset 2 â€” Healthy Baseline
**File:** `data/healthy_baseline.json`
**Size:** 50 records
**Purpose:** Measure false positive rate. Watcher must produce zero events
against this entire dataset.

`seed.py` generates these by randomly sampling from a pool of healthy
message templates and varying the numeric values:

```python

    "Scheduled task completed in {ms}ms",

    "Request queue depth: {n}",
    "Response time {ms}ms within threshold",
    "Replica count stable at {n}",
    "Log rotation completed",
    "Dependency check passed",
    "Startup sequence complete",
]
```

All 50 records use severity INFO. No record contains any string from
`watcher_skills.DETECTABLE_PATTERNS`. This must be enforced in `seed.py`
with an assertion after generation.

---

#### Dataset 3 â€” Mixed Stream
**File:** `data/mixed_stream.json`
**Size:** 100 records
**Purpose:** Test full loop under realistic conditions. Signal hidden in noise.
Used in Experiment 2.

`seed.py` builds this dataset as follows:

1. Take 90 healthy log records sampled from the same templates as Dataset 2
2. Generate 10 failure records â€” at least 2 of each failure type,
   distributed across all 4 types
3. Insert the 10 failure records at random positions in the 90 healthy records
4. Write the combined 100 records in the randomised order to
   `data/mixed_stream.json`
5. Write a separate `data/mixed_stream_ground_truth.json` that records the
   exact index position of each injected failure and its expected action â€”
   used by the harness to verify detection without ambiguity

**Ground truth file structure:**

```json
[
  {
    "index": 7,
    "failure_type": "OOMKilled",
    "expected_action": "scale_memory",
    "expected_params": { "memory": "1Gi" }
  },
  {
    "index": 23,
    "failure_type": "HighLatency",
    "expected_action": "scale_instances",
    "expected_params": { "max_instances": 3 }
  }
]
```

## The Harness

`harness.py` sits at the project root. Controlled experiment runner.
Feeds known inputs, runs the full agent loop, asserts correct outputs,
writes results to SQLite. Plain Python. No test framework.

### What the Harness Does

**Experiment 1 â€” Detection only (Watcher, no Healer)**
- Runs Watcher against `data/clean_failures.json`
- Asserts all 4 failure types detected
- Records detection latency per event

**Experiment 2 â€” Full loop (Watcher + Healer)**
- Resets `infra_state` to baseline before each scenario
- Runs full loop against `data/clean_failures.json`
- Asserts correct `infra_state` mutation per scenario
- Records detect + decide + act + total MTTR

**Experiment 3 â€” Mixed stream (full loop against noise)**
- Runs full loop against `data/mixed_stream.json`
- Compares detections against `data/mixed_stream_ground_truth.json`
- Reports detection rate, false positive rate, resolution rate, MTTR

**Experiment 4 (reference repo extension) â€” Kubernetes-style structured signals**
- `agents/k8s_watcher.py` + `skills/k8s_signal_skills.py`
- Full loop on `data/k8s_clean_signals.json` with K8s-shaped `signal` objects

**Experiment 5 (reference repo extension) â€” Near-real noisy log stream**
- Same scoring as Experiment 3 on `data/near_real_stream.json` (200 records, 20 injected failures, noisy envelopes) vs `near_real_ground_truth.json`

**Integration gate (reference repo)** â€” `harness.py` runs `integrations/validate.py` before experiments.

### Harness Assertions

```python
ASSERTIONS = {
    "OOMKilled":          lambda s: s["app-service"]["memory"] == "1Gi",
    "CrashLoopBackOff":   lambda s: s["app-service"]["restart_count"] == 0,
    "StartupProbeFailed": lambda s: s["app-service"]["port"] == 8080,
    "HighLatency":        lambda s: s["app-service"]["max_instances"] == 3,
}
```

## Definition of Done

The POC is complete when all of the following are true:

1. `data/seed.py` generates all three datasets and passes the healthy
   baseline assertion
2. `data/clean_failures.json` exists with 4 records
3. `data/healthy_baseline.json` exists with 50 records, zero failure patterns
4. `data/mixed_stream.json` exists with 100 records, 10 injected failures
5. `data/mixed_stream_ground_truth.json` exists with 10 entries
6. `skills/watcher_skills.py` defines all detectable patterns
7. `skills/healer_skills.py` defines all decision table entries
8. `agents/watcher.py` imports patterns only from `watcher_skills.py`
9. `agents/healer.py` imports decision table only from `healer_skills.py`
10. `harness.py` runs all three experiments and prints results
11. Experiment 1: all 4 scenarios detected
12. Experiment 2: all 4 scenarios pass assertions
13. Experiment 3: 10/10 detected, 0 false positives, 10/10 resolved
14. Results written to `metrics/results.db`
15. System runs with two commands: `python data/seed.py` then `python harness.py`

**Nothing else is in scope** for the *original* Phase 1 paragraph above.

## Synthetic data vs real-world log corpora

The reference implementation generates **synthetic** JSON for CI, reproducibility, and hygiene.

**You may still use real or open-source log samples** in your own checkout if you:

1. Respect the **dataset license** (attribution, non-commercial clauses, redistribution limits).
2. **Never commit** secrets, customer data, or unredacted production logs to a public repository.
3. **Normalize** raw lines into the project log record shape (`severity`, `service`, `message`, optional `labels`).
4. Understand that Phase 1 agents are **rule-based**, not trained ML models: "training" means extending `DETECTABLE_PATTERNS` and validating with harnesses, not gradient descent on arbitrary dumps.

Place optional local samples under `data/external/` (see `data/external/README.md` and `docs/HELP.md` in the repository).
